## 1. 进度维护约定（开发过程中必须执行）

本文档是该改造的**持续进度台账**，不是一次性静态方案。任何开发者或 Agent 参与本改造时，都必须同步更新本文档。

### 1.1 开始一个里程碑时

必须完成以下更新：

- 将总览表和对应里程碑状态改为 `进行中`。
- 更新文档顶部“最后更新”和“当前里程碑”。
- 填写实际开始日期。
- 记录本里程碑准备采用的实现方案；若与默认方案不同，同步写入“决策记录”。

### 1.2 每次开发会话结束或提交前

必须完成以下更新：

- 更新已完成的任务复选框，不能只修改代码而不更新台账。
- 更新总览表、当前里程碑和“最后更新”。
- 在“开发日志”追加本次完成内容、修改范围、测试命令及结果。
- 记录关联 commit / PR（尚未产生时可填“待提交”）。
- 有性能数据时，填写实测值，不使用“明显变快”等不可验证描述。
- 有未完成事项时，明确写入“下一步”，不要留隐性问题。

### 1.3 完成一个里程碑时

只有同时满足以下条件，才能标记为 `已完成`：

- 范围内任务全部完成，或经记录后明确移出范围。
- 验收标准全部通过。
- 相关自动化测试通过。
- 性能与一致性结果已写入“实际结果”。
- 已记录 commit / PR 和完成日期。
- 已执行需要的回归测试，并填写结果。

### 1.4 阻塞、返工或范围调整

- 阻塞时标记为 `阻塞`，写明具体阻塞条件、首次发生时间、已尝试方案和下一步。
- 不得因为“实现较复杂”直接跳过验收项。
- 返工时保留原日志，追加新记录，不覆盖历史。
- 范围、架构或统计口径发生变化时，必须追加“决策记录”，说明原因和影响。
- 延期或取消任务必须注明移交给哪个里程碑，或注明取消原因。

### 1.5 状态定义

| 状态 | 含义 |
| --- | --- |
| `未开始` | 尚未进入开发 |
| `进行中` | 已开始，但验收尚未全部完成 |
| `阻塞` | 存在明确外部或技术条件阻止继续推进 |
| `待验收` | 实现完成，等待测试、性能或一致性验收 |
| `已完成` | 实现、测试、验收和台账记录均完成 |
| `已取消` | 经决策后不再实施，必须记录原因 |

## 3. 基线与最终验收目标

### 3.1 调研基线

- `/api/usage` 连续三次总耗时：**74.815s / 128.422s / 178.280s**。
- 响应大小：约 **12.3MB**。
- 单次并行直读全部 reader：约 **9.006s**。
- 数据规模：约 **350 个文件、2.34 万条记录**。
- 最慢数据源：DSH、Claude、Qoder、Codex。
- 前端自动刷新：60 秒，无 in-flight 防重入。

### 3.2 最终验收目标

以下是工程目标，不是尚未验证的性能承诺。实际结果必须在对应里程碑中填写。

| 指标 | 目标 |
| --- | --- |
| 请求合并 | 20 个并发同步/查询请求不会触发 20 次实际扫描；同一轮共享结果 |
| 长时间稳定性 | 页面连续运行 30 分钟，不出现扫描积压或延迟逐轮增长 |
| 快照读取 | 本机已有快照时 GET 目标 `<200ms`，不触发原始日志扫描 |
| 未变化刷新 | 日志未变化时一轮增量同步目标 `<1s` |
| 新增量成本 | 追加少量日志时，只读取新增字节/帧或执行明确的依赖重算 |
| 冷导入 | 不阻塞页面和其他 API；有旧快照时先展示旧数据 |
| 响应体积 | 请求日志分页后不再按刷新周期传输全部历史 records |
| 统计一致性 | 记录数、抽样 ID、Tokens、Credits、项目/模型归组与全量基线一致 |
| 主线程响应 | 扫描期间页面和其他本地 API 不被同步解压/解析长任务卡死 |

## 5. M1：前后端 single-flight 与 loading 修复

**状态：待验收**<br>
**目标：先阻止扫描叠加，不改变统计口径和 reader 实现。**<br>
**实施方案：服务端以模块级共享 Promise 合并同轮扫描并记录耗时与实际扫描次数；前端复用同一 in-flight 请求，自动 tick 遇 pending 直接跳过，按文档可见性暂停/补扫，并用请求代次防止旧响应覆盖；首载、后台刷新、手动同步分别维护状态，后台及失败时保留最后成功数据。**

### 范围

- [x] 前端首次、手动和自动加载共享同一个 in-flight Promise。
- [x] 自动 tick 遇到 pending 时跳过，不在后端排队。
- [x] 服务端共享扫描 Promise，并发 GET 不重复执行同一轮扫描。
- [x] 页面隐藏时暂停自动扫描，重新可见时补扫一次。
- [x] 防止旧响应覆盖新数据。
- [x] 首次 loading、后台 refreshing 和手动 syncing 状态分离。
- [x] 后台刷新保留旧卡片、图表和表格。
- [x] 自动刷新失败保留最后成功数据；错误状态可查看。
- [x] 增加基础耗时与实际扫描次数日志，便于后续验证。

### 明确不在本阶段

- 不引入数据库。
- 不改变 reader 的统计语义。
- 不承诺消除单次全量扫描耗时。
- 不强制引入 React Query；可继续使用现有 React 状态。

## 6. M2：本地持久化与扫描/查询分离

**状态：已完成**<br>
**前置：建议完成 M1。**<br>
**目标：GET 不再现场读取全部原始日志，页面可以读取最后成功数据。**<br>
**实施方案：使用项目 `.data/usage.sqlite`（`USAGE_DB_PATH` 可覆盖）与 `node:sqlite` schema v2；在单轮明确批次事务中写入归一化记录、来源、独立去重账本和预序列化最后成功快照，revision 仅随快照内容变化。GET 直接返回持久化快照；`POST /api/usage/sync` 通过受控 `worker_threads` 执行现有全量 reader 并写库，`GET /api/usage/sync` 返回状态。worker 使用 Node 22 原生 TypeScript 与受控模块解析钩子，不新增运行时依赖；首载先 GET 旧快照再触发同步，空库仅展示导入状态，不冒充真实零用量。**

### 范围

- [x] 确定本地数据库位置、schema 版本与迁移策略。
- [x] 建立归一化 `usage_records` 表及必要查询索引。
- [x] 建立 `session_log_sync` 表，保存文件游标和 parser state。
- [x] 建立独立 `usage_dedup` 表。
- [x] 增加最后成功快照和读取失败回退策略。

- [x] 增加 sync/status 能力和 revision。
- [x] 保留现有 GET 响应结构作为过渡，减少前端同步改动。
- [x] 将重扫描与同步解析移出 Next 主线程，或使用受控 worker。
- [x] 明确首次数据库为空时的导入状态和错误状态。
- [x] 数据库写入按文件或明确批次使用事务。

- 优先评估项目当前已经使用的 `node:sqlite`，避免新增原生依赖。

## 7. M3：DSH 帧级增量导入

**状态：已完成**<br>
**前置：M2 的游标、去重和事务能力可用。**<br>
**目标：DSH 刷新成本取决于新增帧，而不是全部会话长度。**<br>
**实施方案：复用现有 Zstd 帧边界扫描；以文件元数据和尾部指纹保护完整帧/行字节游标，未变化文件跳过正文，追加内容仅解压/解析新增完整区间；持久化跨轮 `step/start` parser state。文件截断、重写或续读边界非法时回退该文件全量重建，并由持久去重账本保证幂等；每个文件的记录写入、去重与游标推进在同一事务中提交。**<br>
**实际实施：沿用 schema v2，以来源级最终快照事务原子提交记录、去重、游标和 parser state；文件集变化或可检测的重写/截断/非法边界触发 DSH 来源级全量重建，以重算跨文件去重 winner。原始日志读取与解压为 O(新增)，当前归一化记录聚合和 legacy 快照序列化仍为 O(总记录数)，后者由 M6 继续消除。**

### 范围

- [x] 复用现有 Zstd 帧结构扫描能力。
- [x] 支持从上次完整帧末尾继续读取。
- [x] 只解压新增完整帧。
- [x] 普通 JSONL 只读取新增完整行。
- [x] 游标不越过残缺尾帧或未终结尾行。
- [x] 持久化并恢复未完成的 `step/start` 状态。
- [x] 文件重写或帧边界非法时执行明确恢复策略。
- [x] 通过持久去重账本防止重扫重复入库。
- [x] 记录写入、去重与游标推进使用同一事务。
- [x] 保持全局消息 ID 去重与项目标签语义不变。
