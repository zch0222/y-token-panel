## 1. 进度维护约定（开发过程中必须执行）

本文档是该改造的**持续进度台账**，不是一次性静态方案。任何开发者或 Agent 参与本改造时，都必须同步更新本文档。

### 1.1 开始一个里程碑时

必须完成以下更新：

- 将总览表和对应里程碑状态改为 `进行中`。
- 更新文档顶部“最后更新”和“当前里程碑”。
- 填写实际开始日期。
- 记录本里程碑准备采用的实现方案；若与默认方案不同，同步写入“决策记录”。

### 1.2 每次开发会话结束或提交前

必须完成以下更新：

- 更新已完成的任务复选框，不能只修改代码而不更新台账。
- 更新总览表、当前里程碑和“最后更新”。
- 在“开发日志”追加本次完成内容、修改范围、测试命令及结果。
- 记录关联 commit / PR（尚未产生时可填“待提交”）。
- 有性能数据时，填写实测值，不使用“明显变快”等不可验证描述。
- 有未完成事项时，明确写入“下一步”，不要留隐性问题。

### 1.3 完成一个里程碑时

只有同时满足以下条件，才能标记为 `已完成`：

- 范围内任务全部完成，或经记录后明确移出范围。
- 验收标准全部通过。
- 相关自动化测试通过。
- 性能与一致性结果已写入“实际结果”。
- 已记录 commit / PR 和完成日期。
- 已执行需要的回归测试，并填写结果。

### 1.4 阻塞、返工或范围调整

- 阻塞时标记为 `阻塞`，写明具体阻塞条件、首次发生时间、已尝试方案和下一步。
- 不得因为“实现较复杂”直接跳过验收项。
- 返工时保留原日志，追加新记录，不覆盖历史。
- 范围、架构或统计口径发生变化时，必须追加“决策记录”，说明原因和影响。
- 延期或取消任务必须注明移交给哪个里程碑，或注明取消原因。

### 1.5 状态定义

| 状态 | 含义 |
| --- | --- |
| `未开始` | 尚未进入开发 |
| `进行中` | 已开始，但验收尚未全部完成 |
| `阻塞` | 存在明确外部或技术条件阻止继续推进 |
| `待验收` | 实现完成，等待测试、性能或一致性验收 |
| `已完成` | 实现、测试、验收和台账记录均完成 |
| `已取消` | 经决策后不再实施，必须记录原因 |

## 3. 基线与最终验收目标

### 3.1 调研基线

- `/api/usage` 连续三次总耗时：**74.815s / 128.422s / 178.280s**。
- 响应大小：约 **12.3MB**。
- 单次并行直读全部 reader：约 **9.006s**。
- 数据规模：约 **350 个文件、2.34 万条记录**。
- 最慢数据源：DSH、Claude、Qoder、Codex。
- 前端自动刷新：60 秒，无 in-flight 防重入。

### 3.2 最终验收目标

以下是工程目标，不是尚未验证的性能承诺。实际结果必须在对应里程碑中填写。

| 指标 | 目标 |
| --- | --- |
| 请求合并 | 20 个并发同步/查询请求不会触发 20 次实际扫描；同一轮共享结果 |
| 长时间稳定性 | 页面连续运行 30 分钟，不出现扫描积压或延迟逐轮增长 |
| 快照读取 | 本机已有快照时 GET 目标 `<200ms`，不触发原始日志扫描 |
| 未变化刷新 | 日志未变化时一轮增量同步目标 `<1s` |
| 新增量成本 | 追加少量日志时，只读取新增字节/帧或执行明确的依赖重算 |
| 冷导入 | 不阻塞页面和其他 API；有旧快照时先展示旧数据 |
| 响应体积 | 请求日志分页后不再按刷新周期传输全部历史 records |
| 统计一致性 | 记录数、抽样 ID、Tokens、Credits、项目/模型归组与全量基线一致 |
| 主线程响应 | 扫描期间页面和其他本地 API 不被同步解压/解析长任务卡死 |

## 5. M1：前后端 single-flight 与 loading 修复

**状态：未开始**<br>
**目标：先阻止扫描叠加，不改变统计口径和 reader 实现。**

### 范围

- [ ] 前端首次、手动和自动加载共享同一个 in-flight Promise。
- [ ] 自动 tick 遇到 pending 时跳过，不在后端排队。
- [ ] 服务端共享扫描 Promise，并发 GET 不重复执行同一轮扫描。
- [ ] 页面隐藏时暂停自动扫描，重新可见时补扫一次。
- [ ] 防止旧响应覆盖新数据。
- [ ] 首次 loading、后台 refreshing 和手动 syncing 状态分离。
- [ ] 后台刷新保留旧卡片、图表和表格。
- [ ] 自动刷新失败保留最后成功数据；错误状态可查看。
- [ ] 增加基础耗时与实际扫描次数日志，便于后续验证。

### 明确不在本阶段

- 不引入数据库。
- 不改变 reader 的统计语义。
- 不承诺消除单次全量扫描耗时。
- 不强制引入 React Query；可继续使用现有 React 状态。

### 主要参考

- [当前前端加载逻辑](../src/components/dashboard/usage-dashboard.tsx#L213-L243)

### 验收标准

- [ ] 20 个并发请求只执行一轮实际扫描，调用方获得同一轮结果。
- [ ] 手动点击与自动 tick 同时发生时不会新增第二轮扫描。
- [ ] 页面隐藏时不启动自动扫描，恢复可见后只补一轮。

## 9. M5：Codex 依赖缓存与其余 reader 优化

**状态：未开始**<br>
**前置：M2。**<br>
**目标：减少 Codex 重复解析，同时保证跨文件依赖变化会触发正确重算。**

### Codex 范围

- [ ] 保持“变化文件从头解析”，不直接套用普通字节续读。
- [ ] 缓存父 rollout 解析后的时间线，供多个 fork 共享。
- [ ] 缓存 replay prefix。
- [ ] 缓存 deferred 原因及子文件、父文件依赖状态。
- [ ] 子文件未变化但父文件追加时，能重新尝试 deferred 导入。
- [ ] 父文件替换、轮转或同尺寸变化时，旧时间线失效。
- [ ] 评估 Node.js 可移植的文件身份戳，并补尾部指纹等防御。
- [ ] 保留有界 fork、续写基线和父签名完整性检查。
- [ ] 提供手动重建或缓存版本失效能力。

### 明确禁止

- 不根据子文件 mtime 永久跳过 deferred。
- 不把父时间线缓存建立在没有失效策略的全局 Map 上。
- 不为追求增量而放松“宁可暂缓，也不双算”的现有口径。
